# ADR-004 인가 상태와 로그인 세션을 Redis에 저장

## 배경

인가 서버는 인가 코드, 액세스·리프레시·ID 토큰과 그 메타데이터(인가 상태)를 어딘가에 저장해야 한다. 기본 구현은 메모리에 저장하기 때문에 서버를 재시작하면 토큰이 전부 사라지고, 서버를 여러 대로 늘리면 서로 상태를 공유하지 못한다. 로그인 세션도 마찬가지다.

## 검토한 방법

1. 메모리 (기본 구현)
2. MySQL (`JdbcOAuth2AuthorizationService`)
3. Redis

## 결정

Redis로 했다. 인가 상태는 `RedisOAuth2AuthorizationService`를 직접 구현해서 저장하고, 로그인 세션은 Spring Session으로 Redis에 넣었다.

## 결과

인가 상태는 금방 만료되는 데이터다. 인가 코드는 5분, 액세스 토큰은 10분, 리프레시 토큰은 14일이면 끝난다. 토큰 만료 시각을 그대로 Redis TTL로 쓰면 만료 데이터를 지우는 배치가 필요 없다. MySQL에 넣었다면 정리 배치와 그 부하를 따로 신경 써야 했을 것이다. 또 토큰 조회는 요청마다 일어나는 단건 조회라 키-값 저장소와 잘 맞는다.

Redis 키에는 토큰 원문 대신 SHA-256 해시를 넣었다. 키 목록이 노출돼도 토큰을 알아낼 수 없다.

직렬화는 JDK 직렬화를 썼다. `OAuth2Authorization`과 그 안의 토큰, 인증 주체가 모두 `Serializable`이라 따로 매핑할 필요가 없었다. 단점은 클래스 구조가 바뀌는 배포를 하면 기존 데이터를 못 읽을 수 있다는 것이다. 그런 배포에서는 사용자가 다시 로그인해야 한다. JSON으로 저장하려면 인증 주체 타입마다 Jackson 설정을 따로 관리해야 해서 일단 미뤘다.

Redis가 죽으면 로그인과 토큰 발급이 멈춘다. 다만 메모리 구현은 재시작만 해도 전부 날아가니 그보다 나쁘지는 않고, 운영에서는 Redis 복제로 대응하면 된다.

아직 남은 문제가 하나 있다. Spring Authorization Server가 세션 식별자(`sid`)를 계산할 때 쓰는 `SessionRegistry`는 여전히 메모리 구현이다. 서버를 여러 대 띄우려면 Spring Session의 인덱스 저장소 기반으로 바꿔야 한다.
