# ADR-001 헥사고날 아키텍처와 멀티모듈 채택

## 배경
인증 서버는 수명이 긴 시스템이다. 저장소(MySQL, Redis), 프로토콜(OAuth2, OIDC), 통지 방식(Back-Channel Logout)은 바뀔 수 있지만 계정 잠금, 세션 정책 같은 도메인 규칙은 오래 유지된다. 이 둘이 섞이면 프레임워크 업그레이드나 저장소 교체가 도메인 규칙 수정으로 번진다.

## 선택지
1. 단일 모듈 + 계층형 패키지 (controller / service / repository)
2. 단일 모듈 + 헥사고날 패키지
3. 멀티모듈 + 헥사고날

## 결정
3번. 도메인, 애플리케이션, 어댑터를 Gradle 모듈로 분리하고 의존 방향을 `bootstrap → adapter → application → domain`으로 고정한다.

## 결과
- 장점: 잘못된 의존이 컴파일 단계에서 막힌다 (도메인 모듈에는 Spring이 클래스패스에 없음). 모듈 경계가 곧 팀 간 책임 경계가 된다.
- 단점: 모듈 수가 늘어 빌드 설정이 복잡하다 → Convention Plugin(`build-logic`)으로 공통 설정을 한곳에 모은다.
- 단점: 같은 모듈 안의 패키지 의존은 컴파일러가 막지 못한다 → ArchUnit 테스트로 보완한다.
- 도메인 모델과 JPA 엔티티를 분리하므로 매핑 코드가 생긴다. 도메인이 영속성 제약(기본 생성자, open 클래스, 지연 로딩)에 오염되지 않는 대가로 받아들인다.
