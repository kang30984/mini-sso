# ADR-012 검증된 클라이언트 시크릿 캐시

## 배경
부하 테스트에서 토큰 갱신 요청의 평균 지연이 823ms였다. 같은 실행에서 JWKS 조회는 5.6ms, Argon2 연산이 없는 인가 요청 단계는 약 150ms였다.

토큰 갱신에는 사용자 비밀번호 비교가 없지만, 토큰 엔드포인트는 요청마다 클라이언트를 인증한다. 클라이언트 시크릿은 Argon2로 저장되어 있어 토큰 요청마다 Argon2 비교(약 16MB 메모리, 의도적으로 느린 연산)가 한 번씩 일어난다. 서비스들이 10분마다 토큰을 갱신하면 이 비용이 사용자 수에 비례해 쌓인다. 또한 Argon2가 CPU를 점유하면서 다른 요청까지 느려졌다.

## 선택지
1. 클라이언트 시크릿을 빠른 해시(SHA-256)로 저장
2. Argon2 파라미터를 낮춤
3. 저장은 Argon2 그대로 두고, 검증에 성공한 시크릿을 짧게 캐시

## 결정
3번. Spring Authorization Server가 클라이언트 인증에 쓰는 `PasswordEncoder`만 캐시 데코레이터(`VerifiedSecretCachingPasswordEncoder`)로 감싼다.

- 1번은 시크릿이 충분히 무작위일 때만 안전한데, 지금은 관리자가 시크릿을 지정하므로 그 전제를 보장할 수 없다.
- 2번은 계정 비밀번호 보호 수준까지 낮춘다.

## 결과
- DB가 유출되었을 때의 보호 수준은 그대로다 (저장된 해시는 Argon2).
- 틀린 시크릿은 캐시하지 않으므로 무차별 대입은 매번 Argon2 비용을 그대로 치른다.
- 캐시 키는 SHA-256(원문 + 저장된 해시)라 메모리에 시크릿 원문이 남지 않고, 시크릿을 교체하면 이전 항목은 자동으로 무효가 된다. 항목 수는 클라이언트 수만큼이며 TTL은 10분이다.
- 계정 비밀번호는 캐시하지 않는다. `Argon2PasswordHasher`는 `PasswordEncoder` 빈을 주입받지 않고 캐시 없는 인코더를 직접 쓴다.
- 대가: 캐시 TTL 동안은 같은 인스턴스에서 시크릿 검증이 메모리 비교로 끝난다. 시크릿이 유출되어 교체하는 경우에는 저장된 해시가 바뀌므로 즉시 무효가 된다.
- 효과는 부하 테스트 워크플로의 `client_secret_cache` 입력으로 켜고 끈 결과를 비교해 README에 기록한다.
