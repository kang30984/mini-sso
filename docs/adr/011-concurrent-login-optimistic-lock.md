# ADR-011 같은 계정의 동시 로그인과 낙관적 락

## 배경
부하 테스트(첫 실행)에서 같은 계정으로 동시에 로그인하자 요청의 26%가 500 오류로 끝났다. 서버 로그의 예외 1,447건이 모두 같은 계정 엔티티의 `ObjectOptimisticLockingFailureException`이었다.

로그인에 성공하면 마지막 로그인 시각(`lastLoginAt`)을 갱신하는데, 계정 엔티티에는 `@Version` 낙관적 락이 있다. 같은 계정의 로그인 두 건이 같은 버전을 읽고 각자 커밋하면 늦은 쪽이 실패한다. 이 예외가 인증 실패로 처리되지 않아 500으로 노출됐다. 더블클릭, 여러 기기 동시 로그인처럼 실제로도 일어나는 상황이다.

## 선택지
1. 비관적 락(`SELECT ... FOR UPDATE`)으로 같은 계정의 로그인을 직렬화
2. 충돌 시 재시도만 추가
3. 충돌의 원인인 값을 낙관적 락 대상에서 제외하고, 남는 충돌만 재시도

## 결정
3번.

- `lastLoginAt`, `updatedAt`은 `@OptimisticLock(excluded = true)`로 버전 증가 대상에서 뺀다. 성공한 로그인끼리는 더 이상 충돌하지 않고, 마지막에 커밋한 시각이 남는다. 이 값은 정합성이 중요한 값이 아니다(어느 쪽 시각이 남아도 된다).
- 실패 횟수와 잠금 상태는 보안 규칙이므로 계속 낙관적 락으로 보호한다. 동시에 틀린 비밀번호가 들어와 충돌하면, 트랜잭션 밖(`AccountAuthenticationProvider`)에서 한 번 재시도해 최신 상태로 다시 판단한다. 그래도 충돌하면 500이 아니라 인증 실패로 응답한다.

## 결과
- 정상 사용자의 동시 로그인은 충돌 없이 처리된다 (`ConcurrentLoginIT`로 회귀 검증).
- 비관적 락을 쓰지 않으므로 로그인마다 DB 행 잠금을 잡지 않는다.
- 남은 위험: 한 계정에 틀린 비밀번호를 대량으로 동시에 보내면 재시도까지 충돌한 시도의 실패 횟수가 집계되지 않을 수 있다. 공격자가 얻는 추가 시도는 동시성 수준만큼으로 제한되고, IP당 시도 제한(분당 20회)이 앞단에서 막는다. 더 엄격하게 하려면 실패 횟수를 원자적 UPDATE(`failed_login_count = failed_login_count + 1`)로 바꾸는 방법이 있다.
