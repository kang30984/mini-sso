# ADR-011 같은 계정의 동시 로그인과 낙관적 락

## 배경

처음 부하 테스트를 돌렸을 때 로그인 요청의 26%가 500 오류로 끝났다. 서버 로그를 보니 예외 1,447건이 전부 같은 계정 엔티티에서 난 `ObjectOptimisticLockingFailureException`이었다.

로그인에 성공하면 마지막 로그인 시각(`lastLoginAt`)을 갱신하는데, 계정 엔티티에는 `@Version`으로 낙관적 락이 걸려 있다. 같은 계정으로 두 요청이 동시에 들어와 같은 버전을 읽고 각자 커밋하면 늦게 커밋한 쪽이 실패한다. 문제는 이 예외가 인증 실패로 처리되지 않고 그대로 500으로 나갔다는 점이다. 부하 테스트에서 모든 가상 사용자가 계정 하나를 쓴 탓이 크지만, 더블클릭이나 여러 기기에서 동시에 로그인하는 경우에도 충분히 생길 수 있다.

## 검토한 방법

1. 비관적 락(`SELECT ... FOR UPDATE`)으로 같은 계정의 로그인을 한 줄로 세우기
2. 충돌하면 재시도만 하기
3. 충돌의 원인인 값을 낙관적 락 대상에서 빼고, 나머지 충돌만 재시도하기

## 결정

3번으로 했다.

`lastLoginAt`과 `updatedAt`은 `@OptimisticLock(excluded = true)`를 붙여 버전 증가 대상에서 뺐다. 이제 성공한 로그인끼리는 충돌하지 않고, 마지막에 커밋한 쪽의 시각이 남는다. 어느 쪽 시각이 남아도 상관없는 값이라 이렇게 해도 된다.

실패 횟수와 잠금 상태는 보안 규칙이라 계속 낙관적 락으로 보호한다. 틀린 비밀번호가 동시에 들어와 충돌하면, 트랜잭션 바깥인 `AccountAuthenticationProvider`에서 한 번 재시도해서 최신 상태로 다시 판단한다. 그래도 충돌하면 500 대신 인증 실패로 응답한다.

## 결과

정상 사용자의 동시 로그인은 이제 충돌 없이 처리된다. 같은 상황을 `ConcurrentLoginIT`에서 12개 스레드로 재현해 회귀 테스트로 남겼다.

비관적 락을 쓰지 않으니 로그인할 때마다 DB 행 잠금을 잡지 않아도 된다.

남은 위험도 있다. 한 계정에 틀린 비밀번호를 대량으로 동시에 보내면, 재시도까지 충돌한 시도는 실패 횟수에 들어가지 않을 수 있다. 다만 공격자가 이걸로 얻는 추가 시도는 동시 요청 수만큼이고, 그 앞에서 IP당 시도 제한(분당 20회)이 먼저 막는다. 더 엄격하게 하려면 실패 횟수를 `failed_login_count = failed_login_count + 1` 같은 원자적 UPDATE로 바꾸면 된다.
